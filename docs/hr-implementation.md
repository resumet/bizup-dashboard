# HR 구현 및 검증 기록

기준: `hr_dashboard_prd.md` v1.0의 P0 전체. P1은 이번 출시 범위가 아니다.

- 진입: `/` 선택 → `/work` 기존 업무관리 / `/hr` HR. 기존 서비스 URL 유지.
- 인증: 기존 Supabase 세션, 초대된 활성 HR 직원만 접근. HR 조직·역할은 별도 관리.

- 동시성: 조직별 변경 잠금, 버전 검사, 근태·휴가 유일성 제약. 읽기 권한은 DB에서 먼저 적용.

성능 수치는 Windows 로컬 PostgreSQL 18의 독립 연결 20개로 측정했다. 운영 Supabase의 네트워크 지연·호스팅 자원은 포함하지 않는다. PGlite 보조 측정도 목표를 통과했다. DB 자동화 16개, 브라우저 검증, ESLint 및 Next 프로덕션 빌드가 통과했다. 브라우저 결과·화면·성능 원본은 `tmp/hr-browser/`에 남긴다.

### 추가 복원 검증 (2026-09-14 21:34 KST)

- 네이티브 DB를 `pg_dump`로 백업하고 별도의 `hr_restore` DB로 `pg_restore`했다. 업무 10,002건·근태 60건·휴가 1건·직원 100명의 행 개수가 원본과 일치했다.
- 복원된 인증 ID로 본인 업무·휴가·원래 출근 시각을 조회했다. 비참여 직원의 업무 조회는 404, HR 테이블 직접 조회는 권한 오류로 거절됐다.
- 복원 후 새 업무 배정과 알림 처리가 정상 동작하고, 해당 수신자 알림이 한 건만 생성됐다. 가상 데이터와 격리 DB만 사용했으며 운영 백업은 아직 검증하지 않았다.
- 최신 독립 연결 20개 성능 측정은 업무 목록 57ms, 관리자 현황 696ms, 업무 수정 319ms, 출근 89ms(p95)였다. 재검사 중 업무 목록이 2,203ms로 목표를 넘은 실행도 있었으며 후속 두 실행은 통과했다. 원인을 확인하지 않은 단발성 초과를 숨기지 않으며, 운영 환경 성능은 설치 후 별도로 확인한다.
- 검증기는 성능 목표 초과가 있어도 나머지 항목과 전체 측정 결과를 저장한 뒤 실패하도록 개선했다. 최종 전체 실행은 종료 코드 0이었다.

## 운영 연결에서 확인한 남은 작업

- 최초 검사에서는 `HR_MIGRATIONS_NOT_APPLIED`였으나, 사용자의 SQL 설치 파일 전달 이후 재검사에서 `HR_RPC_PRESENT_AND_UNAUTHENTICATED_ACCESS_DENIED`로 바뀌었다. 운영 HR RPC 설치와 비인증 접근 차단을 확인했다.
- 로컬 환경에는 Supabase API 자격 정보만 있고 SQL 직접 연결 정보가 없다. RPC 설치 확인만으로 전체 마이그레이션·초기 관리자 연결·cron 설치까지 완료되었다고 단정하지 않는다.
- 사용자가 SQL Editor에서 통합 설치 파일을 실행하는 방식을 선택했다. `tmp/hr-install.sql`에 마이그레이션 7개와 지정된 초기 관리자 연결을 포함했다. 지정 이메일의 기존 Auth 계정 존재를 읽기 전용으로 확인했으며, HR 권한 연결은 설치 SQL 실행 시 이루어진다.
- 사용자가 알림 스케줄 SQL 실행 완료와 서비스 주소 `bizup-dashboard.vercel.app`을 전달했다. 로컬 `HR_APP_URL`을 설정하고 앱의 기본 초대 주소에도 반영했다. 관리자 메뉴는 관리자 계정에서 모바일 가로 스크롤 없이 보이도록 `오늘` 바로 다음으로 옮겼다.
- 공개 URL 점검에서 `/login`은 HTTP 200, `/hr`은 HTTP 404였다. 운영 앱에 HR 화면 배포가 필요한 상태이며, 로컬 구현과 실제 운영 배포를 구분한다.
- 초기 HR 관리자 연결, 실제 초대 이메일·리다이렉트, 매분 알림 스케줄러와 운영 백업·복원 검증은 아직 남아 있다.
- 서비스 역할로 초기화 함수의 상태를 확인하는 호출은 자동 승인 검토가 거절해 실행하지 않았다. 상태 검사 스크립트에서 해당 호출을 제거하고 기존 읽기 전용 검사를 유지했다.
- 따라서 운영에서 사용할 수 있는 전체 P0 출시 완료로 표시하지 않는다. 원래 목표를 유지하며 운영 연결 및 미검증 인수 항목까지 확인해야 한다.
