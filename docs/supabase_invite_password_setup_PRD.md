# PRD: Supabase 초대 사용자 최초 비밀번호 설정 흐름 개선

- 문서 버전: 1.0
- 작성일: 2026-10-08
- 대상: 기존 Next.js / React 사이트를 유지보수하는 Codex
- 상태: 개발 요청서 (아직 구현/검증되지 않음)
- 우선순위: P1 — 사용자 초대 온보딩 장애 해결

## 0. Codex에게 내리는 실행 지시

**이 문서는 신규 사이트 제작 지시가 아니라 기존 프로젝트를 최소 변경하는 작업 지시다.** 먼저 저장소와 기존 인증 구조를 조사하고, 현재 동작을 재현한 뒤 필요한 파일만 수정하라. 기존 로그인, 로그아웃, 비밀번호 재설정, 회원 역할/권한, 보호 라우트, 데이터베이스 정책, UI 디자인을 보존하라. 프로젝트 구조·URL·기술 스택을 확인하지 않은 상태에서 예시 파일을 무작정 생성하거나 기존 인증 구성을 덮어쓰지 말 것.

1. 저장소의 Next.js 버전, App Router/Pages Router 여부, `src/` 사용 여부, JS/TS, Supabase 패키지 버전, auth 관련 파일을 파악한다.
2. 사용자 초대의 실제 호출 경로(Supabase Dashboard의 Invite User 또는 서버의 `inviteUserByEmail`)와 이메일 템플릿, Site URL, Redirect URLs를 확인한다.
3. 이메일 링크 클릭 후 `/login`으로 이동하는 원인을 **토큰, 리다이렉트, 쿠키 세션, middleware/proxy, 인증 가드** 순으로 조사한다.
4. 기존 구조에 맞추어 초대 인증 → 비밀번호 설정 → 서비스 진입 흐름을 구현한다.
5. 타입 검사, 린트, 빌드, 테스트를 실행하고 변경 파일, 원인, 검증 결과, 운영자 수동 설정 항목을 보고한다.
6. 프로젝트 접근 권한·Supabase 대시보드 권한이 없어 확인할 수 없는 부분은 추측하지 말고 `운영자가 해야 할 일`로 분리한다.

## 1. 배경 / 현재 문제

관리자가 Supabase Authentication에서 사용자를 추가하고 초대 이메일을 발송한다. 사용자가 메일의 링크를 클릭하면 최초 비밀번호를 지정해야 하지만, 현재 서비스의 일반 로그인 화면으로 이동한다. 초대 승인과 세션 설정이 누락되거나 인증 가드가 초대 처리 경로를 차단할 가능성이 있다. 정확한 원인은 기존 코드 및 실제 초대 URL 조사 후 확정한다.

### 목표

- 초대받은 사용자에게 **비밀번호 설정 화면**을 제공한다.
- 초대 토큰을 서버에서 검증한 후 정상적인 Supabase 로그인 세션을 생성한다.
- 비밀번호 저장 성공 시 별도의 로그인 재입력 없이 기존 서비스의 적절한 로그인 후 페이지로 이동한다.
- 기존 이용자의 로그인 기능과 권한/역할 관리에는 회귀가 없다.
- 만료·사용 완료·잘못된 초대 링크는 명확한 오류 화면과 안전한 재초대 안내를 제공한다.

### 범위 제외

- Supabase Auth를 다른 인증 서비스로 교체
- 기존 사용자 비밀번호 강제 변경
- 신규 공개 회원가입 기능 구현
- 역할/권한 체계 재설계, RLS 완화
- 대규모 UI 리뉴얼 또는 DB 스키마 변경 (필수임이 입증되지 않는 한 금지)

## 2. 목표 사용자 흐름

1. 관리자가 기존 방식대로 이메일을 입력해 사용자를 초대한다.
2. 신규 사용자가 초대 메일에서 `초대 수락` 링크를 클릭한다.
3. Next.js의 인증 콜백이 Supabase 초대 토큰을 검증하고 세션을 쿠키에 저장한다.
4. 성공 시 `/set-password`와 같이 **로그인된 초대 사용자를 위한** 비밀번호 설정 화면을 표시한다.
5. 사용자가 새 비밀번호를 2회 입력하고 제출한다.
6. `supabase.auth.updateUser({ password })`가 성공하면 기존 로그인 후 랜딩 페이지로 이동한다.
7. 로그아웃 후 새 비밀번호로 정상 로그인할 수 있다.

> 이미 기존 사이트에 `/auth/callback`, `/auth/confirm`, `/update-password` 등의 적절한 흐름이 있다면 가능한 한 이를 재사용한다. 이 문서의 경로명은 제안이며 하드코딩 요구 사항이 아니다.

## 5. 기술 설계

### 5.1 인증 방식

**권장: Supabase SSR + 서버 콜백에서 초대 토큰 검증.** Supabase 문서의 이메일 템플릿에서 `{{ .TokenHash }}`를 전달하고 서버에서 `verifyOtp({ token_hash, type: 'invite' })`를 호출하는 패턴을 사용한다.

예시 Invite user 이메일 버튼 (실제 환경 및 기존 경로에 맞춰 수정):

```html
<a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=invite">
  초대 수락 및 비밀번호 설정
</a>
```

- 이 변경은 **Confirm signup 템플릿이 아닌 Invite user 템플릿**에 적용한다.
- Site URL이 실제 배포 도메인인지 확인한다.
- 기존 템플릿에 `{{ .RedirectTo }}` 사용, 다중 도메인 또는 preview 환경 지원이 있으면 기존 의도를 분석하고 호환성을 유지한다.
- 이메일 추적 기능의 URL rewrite나 보안 스캐너가 링크를 미리 방문하는 문제가 있는지 점검한다. GET 클릭에서 토큰을 소비하는 구현은 메일 보안 스캐너에 의해 링크가 먼저 사용될 수 있다. 해당 환경에서는 사용자 클릭 확인 후 검증하는 방식 등 대안을 검토한다.
- **링크를 임의의 외부 `next`/`redirect_to` URL로 전달하지 말 것.** 사용자 입력 기반 리다이렉트는 동일 출처 및 허용 경로만 사용할 것.

### 5.2 서버 콜백

권장 경로: `app/auth/confirm/route.ts` (실제 앱 구조에 따라 조정)

필요 로직:

1. URL에서 `token_hash`, `type` 획득.
2. `type === 'invite'`이고 토큰이 있는지 확인. 다른 인증 타입도 동일 경로를 사용 중이면 기존 타입을 깨지 않도록 분기 처리.
3. 기존 프로젝트의 **요청/응답 쿠키에 올바르게 연결된 SSR Supabase 서버 클라이언트**를 사용해 `verifyOtp({ token_hash, type: 'invite' })` 수행.
4. 검증 성공 시 세션 쿠키가 실제 최종 리다이렉트 응답에 반영되는지 확인. `NextResponse.redirect`를 새로 만들어 기존 `Set-Cookie`가 사라지는 구조라면 올바르게 전달되도록 수정한다.
5. 성공 시 내부 경로 `/set-password`로 리다이렉트.
6. 오류 시 `/login?error=invite_invalid` 등 비민감 에러 코드로 보내거나 전용 오류 화면 표시. 원본 토큰/세션을 URL·로그·클라이언트 오류 메시지에 넣지 않는다.
7. 인증 성공 후 민감 토큰이 브라우저 주소창의 최종 URL에 남지 않게 한다.

**중요:** 단순 `verifyOtp()` 성공만으로 끝났다고 간주하지 말 것. 콜백 리다이렉트 후 SSR 쿠키 세션이 유지되는지 반드시 테스트한다.

### 5.3 비밀번호 설정 페이지

권장 경로: `/set-password`

- 기존 디자인 시스템/컴포넌트(입력창·버튼·오류 표시·로딩 상태)를 사용한다.
- 인증된 사용자만 진입 가능하도록 **서버 수준에서** 세션 검사한다. 페이지의 클라이언트 `useEffect` 검사만으로 접근 제어를 끝내지 말 것.
- 초대 인증 직후 사용자에게 최초 비밀번호 등록 폼을 제공한다.
- 비밀번호 및 확인 입력란, 불일치 에러, 제출 중 이중 클릭 방지, 성공 피드백 제공.
- 프로젝트의 Supabase 비밀번호 정책과 일치하도록 길이·문자 조건을 검사하되, 최종 정책 판단은 Supabase 오류 응답을 기준으로 한다.
- Supabase 브라우저 클라이언트로 `auth.updateUser({ password: newPassword })` 호출. 서버 액션을 쓰는 기존 구조면 해당 방식으로 일관되게 구현한다.
- 성공하면 현재 세션을 보존한 상태로 기존 로그인 후 기본 경로로 이동한다.
- 오류 시 현재 페이지에서 이해 가능한 안내를 제공하고 재시도할 수 있게 한다. 실제 비밀번호는 저장/로깅/분석 이벤트에 포함하지 않는다.
- **재방문 통제:** 단순히 로그인했다는 이유만으로 최초 비밀번호 설정 페이지를 허용할지 확인한다. 초대 완료 여부를 별도로 정확하게 제한해야 한다면 서버가 관리하는 상태/권한을 활용한다. 사용자 수정 가능한 `user_metadata`만으로 접근 권한을 결정하지 말 것.

### 5.4 Middleware/Proxy 및 기존 인증 가드

- Next.js 버전에 따라 `middleware.ts` 또는 `proxy.ts`를 조사하고 기존 프레임워크 권고에 맞춘다.
- `/auth/confirm`을 비로그인 사용자도 호출할 수 있도록 한다.
- `/set-password`는 정상 세션을 가진 초대 사용자에게 접근을 허용한다. 다른 화면에서 강제로 `/login` 이동시키지 않는다.
- 동일 도메인 쿠키, SSR 갱신, redirect 체인에서 세션 유지 확인.
- 기존 보호 화면의 인증/권한 검사와 RLS는 유지한다.
- 불필요하게 `getSession()`의 클라이언트 상태만 신뢰해서 서버 접근 권한을 판정하지 말고 Supabase 권고 `getUser()`/`getClaims()` 흐름을 검토한다.

### 5.5 초대 메일 전송 코드가 있는 경우

기존 코드가 `auth.admin.inviteUserByEmail(email, { redirectTo })`를 사용한다면:

- `redirectTo`가 기존 로그인 페이지로 고정되어 있는지 확인한다.
- 실제 콜백/이메일 템플릿의 `{{ .SiteURL }}` 또는 `{{ .RedirectTo }}` 설계와 일치하게 변경한다.
- admin API는 서버 전용에서만 사용하며 secret/service_role 키는 클라이언트에 노출하지 않는다.
- 일반 이용자가 관리자 초대 API를 호출할 수 없도록 기존 권한을 유지한다.

### 5.6 Supabase Dashboard 수동 변경 항목

Codex가 Dashboard를 직접 수정할 수 없다면 아래 항목을 그대로 운영자 체크리스트로 출력한다.

- **Authentication → URL Configuration → Site URL**: 실제 서비스 출처(origin)
- **Authentication → URL Configuration → Redirect URLs**: 실제 인증 처리에서 쓰는 허용 URL(개발·배포·preview 환경 구분)
- **Authentication → Email Templates → Invite user**: 초대 버튼의 링크를 현재 구현한 `token_hash` + `type=invite` 기반 URL로 변경
- 확인용 테스트 메일 발송 및 링크 URL 검사. 토큰 문자열은 보고서에 복사하지 않는다.

> `{{ .SiteURL }}`을 쓰면 Site URL 값이 올바른지가 특히 중요하다. `{{ .RedirectTo }}`를 도입할 경우에도 초대 API 옵션과 허용 URL의 동작을 확인해야 한다.

## 6. 에러/예외 처리

| 상황 | 기대 동작 |
|---|---|
| 초대 링크 정상 | 세션 생성 → 비밀번호 설정 화면 |
| 링크 만료/이미 사용 | 안전한 오류 안내, 새 초대 요청 가이드 |
| 토큰 누락/변조 | 로그인으로 무작정 보내지 말고 초대 링크 오류를 설명 |
| 이메일 링크 보안 스캐너가 선방문 | 재현/원인 분석, 필요시 클릭 확인 또는 OTP 방식 검토 |
| 콜백 성공 후 세션 쿠키 누락 | `/login`으로 튀는 문제 재현 후 응답 쿠키 흐름 수정 |
| 브라우저 기존 로그인 세션이 다른 계정 | 계정 혼선이 없도록 확인하고 안전한 분기 제공 |
| 비밀번호 정책 위반 | Supabase 메시지를 사용자 친화적으로 안내 |
| 네트워크 실패 | 재시도 UI, 중복 요청 방지 |
| 초대된 사용자의 역할 미할당 | 권한 우회 없이 기존 접근 제어 로직에 맞게 처리 |

## 7. 보안 요구사항

- 프론트 코드/`NEXT_PUBLIC_*` 환경변수에 `service_role` 또는 secret API key를 넣지 않는다.
- 초대 토큰과 비밀번호는 로그, 에러 수집, analytics, 브라우저 URL(인증 완료 후)에 남기지 않는다.
- 오픈 리다이렉트 방지: 외부 출처로 임의 리다이렉트 불가.
- 인증 여부 및 계정 권한은 신뢰 가능한 서버 측 검증 사용.
- `raw_user_meta_data`/`user_metadata`를 RLS/권한 판단의 근거로 사용하지 않는다.
- 기존 RLS 정책을 완화하거나 비활성화하지 않는다.
- auth 콜백 및 비밀번호 설정 화면은 토큰/개인정보를 CDN에 캐싱하지 않도록 확인한다.
- 잠재적 초대 사용자 이메일 열거가 가능해지는 에러 문구를 피한다.
- 패키지는 기존 버전과 호환성을 확인하고 lockfile로 고정한다.

## 8. 테스트 계획

### 자동 검증 (가능한 범위에서 구현)

- 초대 성공 시 `verifyOtp`의 `type: 'invite'` 호출 및 안전한 내부 리다이렉트
- 토큰이 없거나 잘못되면 오류 분기
- 세션 유실 시 비밀번호 설정 화면 접근 제한
- 올바른 비밀번호/확인 값만 제출 가능
- `updateUser` 에러 표기 및 중복 제출 방지
- 기존 로그인/비밀번호 재설정 기능 회귀 확인
- `npm run lint`, 타입 검사, `npm run build` 등 실제 프로젝트 스크립트 실행

### 수동 E2E (실제 초대 메일 권장)

1. 비로그인 상태, 시크릿 창에서 미사용 이메일로 초대 받기
2. 받은 메일의 초대 링크 1회 클릭
3. 콜백 성공 후 `/set-password` 표시 (로그인 페이지로 강제 전환되지 않음)
4. 비밀번호 불일치/정책 위반 오류 확인
5. 정상 비밀번호 제출 및 기존 대시보드로 이동
6. 로그아웃 후 새 이메일/비밀번호로 로그인
7. 이미 사용한 링크, 만료 링크, 변조된 링크 처리
8. 기존 계정의 일반 로그인/로그아웃/비밀번호 찾기 확인
9. Chrome 및 메일 앱 내장 브라우저 등에서 필요 시 테스트

**작업을 실제로 실행하지 못한 테스트는 `통과`로 기재하지 말 것.** `미실행(사유)`로 보고한다.
