# DB 마이그레이션 운영

## 2026-09-29 기준선

운영 DB의 현재 구조를 `supabase/migrations/202609290002_production_baseline.sql`에 기록했습니다. 과거 SQL 91개는 내용을 바꾸지 않고 `supabase/migrations_archive/20260929`에 보관합니다. 아카이브에는 중복 버전·손상된 SQL·과거 데이터 삭제/보정 작업이 포함되어 있으므로 배포에 사용하지 않습니다.

기준선 전환은 **운영 스키마나 업무 데이터를 다시 만들지 않고 마이그레이션 이력만 교체**하는 작업입니다. 운영에서 기준 파일을 실행하지 않습니다. 이력이 유실되거나 다른 환경에서 기준선이 미적용으로 보이면 `db push`부터 실행하지 말고 실제 DB 구조와 이력을 먼저 대조하세요. 파일 첫 단계의 보호문도 기존 업무 테이블이 있는 DB에서는 실행을 거절합니다.

기준 파일에는 `public`, `hr`, `personnel_private` 구조와 함수·제약·인덱스·RLS·권한, `auth.users`의 앱 트리거 3개, Storage 정책 11개가 포함됩니다. 추가로 버킷 설정 6개, 공통 서비스 설정 7개, 시스템 메시지 템플릿 1개, `bizup-hr-notifications` 예약 작업 설정을 포함합니다. 사용자·강의·수강생·인사·급여·업로드 파일 데이터는 포함하지 않습니다.

## 이후 변경과 배포

```sh
npm run db:check
supabase migration new describe_change
# 생성된 새 SQL에 변경 작성 및 별도 개발 DB에서 검증
supabase migration list --linked
supabase db push --linked --dry-run
# 대상 프로젝트 및 새 파일 목록 확인 후에만 실행
supabase db push --linked
```

- `.env.local`의 프로젝트와 `supabase/.temp/project-ref`의 연결 대상을 확인합니다. 비밀키를 출력하거나 커밋하지 않습니다.
- 기준선과 적용 완료된 SQL은 수정하지 않고 새 마이그레이션을 만듭니다.
- Dashboard SQL Editor나 별도 스크립트로 구조만 바꾸고 이력 기록을 생략하지 않습니다.
- 불일치를 강제로 넘기기 위한 `--include-all`, 운영 `db reset --linked`, 과거 SQL 일괄 실행은 금지합니다.
- 기존 `npm run db:personnel`은 폐기되어 안내 후 중단합니다. 아카이브 경로를 읽는 테스트는 격리된 테스트 DB 전용입니다.
- `db:check`는 중복 버전, 기준선 변경, 아카이브 누락·변경을 검사합니다. DB와 실제로 대조하는 명령은 아니므로 `migration list`와 `--dry-run`도 확인합니다.

## 새 빈 환경

기준선은 PostgreSQL 17 이상인 **Supabase 환경**을 대상으로 합니다. 관리형 `auth`·`storage` 스키마와 Supabase 역할이 먼저 준비되어 있어야 하며, 일반 PostgreSQL만으로 전체 플랫폼이 설치되지는 않습니다. `pgcrypto`, `uuid-ossp`, `pg_cron`을 사용할 수 있어야 합니다. 앱 스키마가 비어 있는 개발 프로젝트에만 기준선을 적용합니다.

플랫폼 소유 `supabase_admin` 기본 권한은 Supabase가 제공하는 상태를 사용합니다. 기준선은 `postgres`의 공용 스키마 기본 권한을 임시 해제한 후 원래 상태로 복원하여, 제한된 테이블·함수에 불필요한 권한이 생기지 않게 합니다.

기존 프로젝트의 관리자 식별 로직도 함수 정의에 보존되어 있습니다. 다른 프로젝트를 새로 운영할 때는 관리자 설정, 인증·메일·Storage 환경 설정, HR 초기 설정, 시크릿을 별도로 검토해야 합니다. 기준선은 실제 데이터나 업로드 파일의 복구본이 아닙니다.

## 백업과 되돌리기

작업 전 구조 덤프·관리형 스키마 덤프·기존 이력 원본·설정은 로컬 `backups/supabase/20260929-baseline/`에 보관합니다. 이 폴더는 Git에 올리지 않습니다. 소스코드와 별도로 안전한 백업 위치에도 보관하세요. 기준선 및 과거 파일 체크섬은 저장소의 각 manifest에 기록합니다.

`restore-history.sql`은 전환 직후의 기준선 이력만 존재할 때 기존 8건을 복구하는 **이력 전용** 복구문입니다. 운영 테이블·업무 데이터를 변경하지 않습니다. 후속 마이그레이션이 있으면 보호문이 중단하므로 자동 수정하지 말고 먼저 별도 검토합니다. 되돌릴 때는 로컬 활성 마이그레이션도 전환 전 파일 구성으로 함께 맞춰야 합니다. 기준 파일이나 과거 SQL을 운영에 재실행하는 방식으로 되돌리지 않습니다.

## 검증 범위

운영의 카탈로그와 별도 PostgreSQL 17 테스트 DB에 복원한 카탈로그를 비교합니다. 테이블·컬럼·제약·함수·트리거·정책·뷰·시퀀스·권한·기본 권한을 포함하며, 이력 교체 후에도 운영 카탈로그가 바뀌지 않았는지 재확인합니다.

Windows 테스트 DB에서는 `pg_cron` 실행 엔진을 사용할 수 없어 예약 작업의 등록 함수만 격리된 대체 구현으로 검증합니다. 실제 알림 발송이나 운영 예약 작업 실행은 테스트하지 않습니다. 운영의 기존 예약 작업은 변경하지 않으며 설정이 그대로인지 조회로 확인합니다. 과거 기능 테스트의 통과는 새 기준선 복원 검증과 별개입니다.

전환 시 확인 결과: 카탈로그 2,259개 항목이 줄바꿈 차이 외 동일했고, 운영 이력 교체 전후의 카탈로그는 완전히 같았습니다. 이력 교체·원본 복구·동시 변경 거절을 로컬에서 검증했습니다. CLI는 기준선 1건의 로컬/운영 일치와 `upToDate: true`를 반환했습니다. 회귀 테스트는 서비스 테스트 419개와 일반 React 조건의 WBS 컴포넌트 테스트 6개가 통과했고, 선택적 샘플 XLSX 테스트 3개는 파일 미존재로 건너뛰었습니다. WBS 컴포넌트 테스트는 `react-server` 조건 없이 실행해야 합니다.
